## 3 gold_live is the pinned workload in influx mode

The reference is `tests/fixtures/gold_live` (feature sha256 55220f06…, steps.py 74a04258…). It is checked against `config/workload.yaml` (56eec4ed…) and the v3 task texts (`inputs/workload/{kestrel,tessera}_task_v3.md`):

- **Write:** 10 sequential `POST /api/v2/write?org&bucket&precision=ms` requests, 100 points each. Measurement `benchmark`, tag `host=h{index%5+1}` (20 points per host per batch), one integer field `value`, ms timestamps 1 s apart with the last point 1 s before now, uncompressed, one client. Matches.
- **Read:** 20 identical sequential `POST /api/v2/query?org`. The Flux is `range(start: -2h)`, `_measurement == "benchmark"`, `host == "h1"`, `limit(n: 25)`. Matches. `workload.yaml`'s `query_template` has no measurement filter, but the v3 task text says "points of series `benchmark`". gold follows the task text.
- **Delete:** one `POST /api/v2/delete?org&bucket` with predicate `_measurement="benchmark" AND host="h1"`, from 1970-01-01T00:00:00Z to 2100-01-01T00:00:00Z. Matches.
- The engine's `evaluate_conformance` (criteria v2) on the planned requests gives ok=True, spec_coverage 1.0 and no deviations (§7, check 8).

Caveats:

- The module docstring of gold_live still says "workload v2", but the code is v3.
- `tests/fixtures/gold_live/evaluation/` is a stale v2 run from 2026-08-27 with 1 request per operation.
- There is no influx-mode v3 task text: `influxdb_l2_task.md` is v1 (1 batch, ns, limit 10, -1h).
- `results/artifacts` has no `_gold_live` series. `_ref_live` will be gold_live's first measured series under v3.

## 5 Request comparison (planned; read from code, not observed on the wire)

| op | count / order | gold_live (urllib.request) | bddbench_pinned (influxdb-client 1.49.0) |
|---|---|---|---|
| write | 10, sequential, first | `POST /api/v2/write?org=benchmark&bucket=benchmark&precision=ms`; `Content-Type: text/plain; charset=utf-8`; body 100 lines `benchmark,source=gold,host=hN value=<i>i <ms>` (5389 B in batch 1); new TCP connection per request (`Connection: close`) | same path and parameter order (write_service.py: org, bucket, precision); same Content-Type; body 100 lines `benchmark,host=hN,source=gold value=<i>i <ms>` (tags sorted by the client, same points and same byte length per batch); one keep-alive connection for all 10 (one `bench_client`); 100 `Point` objects built and serialised before each request |
| read | 20, sequential, second | `POST /api/v2/query?org=benchmark`; `Content-Type: application/vnd.flux`, `Accept: application/csv`; raw Flux, one line, 151 B; response plain CSV with header | `POST /api/v2/query?org=benchmark`; `Content-Type: application/json`, `Accept: application/json`; JSON `{"extern":{"imports":[],"body":[]},"query":"<Flux>","dialect":{"header":true,"delimiter":",","annotations":["datatype","group","default"],"commentPrefix":"#","dateTimeFormat":"RFC3339"}}`, 380 B; the Flux is multi-line in bracket notation (`r["host"] == "h1"`) with the same semantics; response annotated CSV (3 annotation rows plus header); new client and TCP connection per query |
| delete | 1, last | `POST /api/v2/delete?org=benchmark&bucket=benchmark`; `Content-Type: application/json`; `{"start": "1970-01-01T00:00:00Z", "stop": "2100-01-01T00:00:00Z", "predicate": "_measurement=\"benchmark\" AND host=\"h1\""}` | identical path, Content-Type and body bytes (`json.dumps` of the same key order); plus `Accept: application/json` |
| other | 0 | none | none: no ping, `/health`, bucket lookups, count queries, KPI export or ssh |

Unavoidable differences, all part of using bddbench's client as-is:

1. The read body is JSON with dialect and annotations, and the response is annotated CSV, because bddbench calls `query_csv` with the default dialect.
2. `User-Agent: influxdb-client-python/1.49.0` instead of `Python-urllib/3.14`, and `Accept: application/json` on every request.
3. Write connections are kept alive by urllib3, while gold opens a new connection per request.
4. Client-side CPU between requests is different: Point objects for every batch, and a new `InfluxDBClient` for every query. This happens inside each operation's active span. It therefore enters `throughput_ops_s` (requests divided by active span) but not the proxy latency, which runs from proxy to upstream.
5. Startup imports of `influxdb_client` and `reactivex` and three Background passes make `window_duration_s` longer. Per-operation metrics are not affected.
6. Error semantics: bddbench records HTTP errors and does not fail the step, so behave exits 0 even when requests fail. gold asserts. Failures still show up through conformance (`semantics_ok`) and the proxy `error_count`.

What is the same:

- No gzip (`compression "none"` → `enable_gzip=False`, so no `Content-Encoding`).
- `precision=ms` is a query parameter in both. The precision comes from the `Point`s (write_api.py:369-381, _base.py:477-480).
- One POST per `write()` call, with no splitting into smaller batches (synchronous mode).
- No automatic retries (`retries=False`, rest.py:60).

## 10 Risks and unverified points

- The fixture was never executed. Headers, the JSON query body and the client behaviour were reconstructed by reading influxdb-client 1.49.0 (wheel extracted in the scratchpad), not observed. The pilot verifies them, via `summary.json` → `proxy_stats.requests`.
- `bddbench` is not a default dependency group. A concurrent exact `uv sync` in the shared repo would remove it. The runner stops the series if that happens. Alternative: `default-groups` in pyproject (author's decision).
- `setuptools` is resolved freshly by uv (bddbench locks 80.9.0). The repo uses Python 3.14 with the GIL; bddbench used 3.14 free-threaded. Neither matters for one sequential client, but both are noted.
- CSV race: `replace_metric_rows` rewrites the whole `results/raw/metrics.csv`. No other evaluate may run during the main series. The runner checks only the file's mtime and the ports.
- The scratchpad is temporary. Before the main-series data is used, copy `bddbench_pinned/` (fixture, PROVENANCE.md, changes.diff, build_manifest.json, tools) to a durable place. That is a repo change and needs the author's go. The run directories keep only copies of feature and steps.
- Epochs 18/19 exist only through env overrides. The epoch comment in `config/default.yaml` and the Arbeitsprotokoll need entries in phase 2.
- The `source=gold` tag (C11) is a deliberate byte-equality choice and can be reversed.
- The Flux claim in C15 (`exists r["value"]` drops every unpivoted row) is reasoning only. It no longer affects the port.
